# Complete Guide: BMC + Ironic in Real Datacenters
## Day-0 (Hardware Intake) → Day-2 (Operations) → Cleanup

---

## Executive Summary

After a truck unloads servers at a datacenter, the journey is:

1. **Day-0 (Trucking → Ready for Ironic)**: Physical racking, power/network wiring, BMC configuration
2. **Day-2 (Production Ops)**: Ironic manages provisioning, updates, monitoring, scaling
3. **Cleanup (Decommission)**: Secure wipe, removal, asset recovery

**Key players:**
- **DC Tech**: Racks servers, cables power/network
- **Network Team**: Configures switching, VLANs, IP addressing
- **Platform/Infra Team**: Sets up BMC credentials, runs Ironic, deploys OS
- **BMC (Baseboard Mgmt Controller)**: Hardware chip enabling remote power/console access via IPMI/Redfish
- **Ironic Conductor**: Automation engine that talks to BMCs to provision bare metal

---

## Part 1: The Physical Layer - What Is BMC?

### BMC (Baseboard Management Controller) Overview

**Location:** Tiny service processor soldered onto every server's motherboard  
**Network:** Connected via dedicated OOB (Out-of-Band) network interface  
**Protocols:** IPMI (legacy) or Redfish (modern, RESTful)  
**Power:** Has own power; remains active even when server is off  

**What BMC can do (out of band = doesn't require OS):**
- Power on/off server
- Read sensor data (temperature, fans, power usage)
- Capture console output (virtual serial port)
- Reset, reboot, graceful shutdown
- Update firmware/BIOS
- Set boot order (PXE, disk, USB)

**Why it matters in datacenters:**
- Automation tools (Ironic) use BMC to manage thousands of servers without logging into OS
- When server goes down, you can power cycle it remotely
- You can PXE-boot a server from the network without touching it
- One datacenter operator can manage 1000s of servers via automation

### Step 3: Power Wiring

**Who:** DC technician + facilities team  
**Time:** ~30 min  
**Output:** All servers connected to redundant PDUs, power flow mapped

#### Real Example

```
Each Dell R750 has 2 power supplies (PSU1, PSU2) for redundancy
Each PDU (Power Distribution Unit) has 24 ports
Rack has two PDUs: PDU-A (odd circuits) and PDU-B (even circuits)
   → 1st PSU connects to PDU-A (Breaker 1)
   → 2nd PSU connects to PDU-B (Breaker 2)
   → If PDU-A fails, PDU-B keeps servers on

Power mapping for Rack-3:

SERVER 1 (A-DC1-001):
  - PSU1 (Primary) → PDU-A-03 port 01 (labeled "R3-S1-PSU1")
  - PSU2 (Backup)  → PDU-B-03 port 01 (labeled "R3-S1-PSU2")

SERVER 2 (A-DC1-002):
  - PSU1 → PDU-A-03 port 02
  - PSU2 → PDU-B-03 port 02

... repeat for all 20 servers ...

Verification:
  - PDU-A-03 ports 01-20: all occupied
  - PDU-B-03 ports 01-20: all occupied
  - All cables tucked in cable trays, not blocking airflow
  - All power cables at least 1m away from network cables (EM interference)
  - Breakers not overloaded (each PSU ~500W, total 20 PSUs = 10kW, OK)

Update CMDB for each server:
  Asset A-DC1-001 {
    power: {
      psu1: PDU-A-03:01,
      psu2: PDU-B-03:01,
      total_watts: 500
    }
  }
```

**Output:** All servers powered, redundancy configured.

### Step 5: BMC IP Assignment & Credential Setup

**Who:** Platform/Infrastructure team  
**Time:** ~30 min  
**Output:** All BMCs accessible remotely via IP, credentials secured

#### Real Example

```
Goal: Every BMC gets an IP on VLAN 1000 OOB network

METHOD 1: DHCP with Reservation (Preferred at scale)
  - Network team configures DHCP server to:
    - MAC: 00:11:22:33:44:01 → Reserve IP 10.0.0.45
    - Hostname: bmc-a-dc1-001
    - Gateway: 10.0.0.1
    - DNS: 10.0.0.10

  Servers power on → BMC requests DHCP → gets 10.0.0.45
  CMDB updates automatically via webhook

METHOD 2: Static Assignment via BMC Console (manual, per-server)
  - Tech with laptop and console cable:
    1. Attach to BMC serial console (RJ45 → USB adapter)
    2. Power on server
    3. Watch for BMC BIOS/menu → press hotkey (DEL or F2)
    4. Configure NIC settings:
       - IP: 10.0.0.45
       - Netmask: 255.255.255.0
       - Gateway: 10.0.0.1
       - Save, reboot
    5. Verify with `ping 10.0.0.45` from DC network

Step 5a: Credential Setup (Critical for security)

For each BMC (automated via Ansible):

```ansible
---
- name: Configure BMC credentials
  hosts: localhost
  vars:
    servers:
      - { asset: "A-DC1-001", bmc_ip: "10.0.0.45", 
          serial: "1XJ7HT2" }
  tasks:
    - name: Change BMC root password
      ipmi_power:
        name: "{{ item.bmc_ip }}"
        user: "root"
        password: "CHANGEME"
        new_user_password: "{{ secure_bmc_password }}"
    
    - name: Create ironic service account on BMC
      redfish_config:
        category: Accounts
        command: CreateAccount
        baseuri: "{{ item.bmc_ip }}"
        username: "root"
        password: "{{ secure_bmc_password }}"
        account_details:
          UserName: "ironic-bmc"
          Password: "{{ secure_ironic_bmc_password }}"
          RoleId: "Administrator"
    
    - name: Enable Redfish API
      redfish_config:
        category: Sessions
        command: StartSession
        baseuri: "{{ item.bmc_ip }}"
        username: "ironic-bmc"
        password: "{{ secure_ironic_bmc_password }}"
```

Step 5b: Verify BMC Connectivity

```bash
# From Ironic conductor node (on DC mgmt network):

for i in {45..64}; do
  bmc_ip="10.0.0.$i"

```

    "redfish_verify_ca": false

    "local_gb": 1000

}

{

  "name": "bm-a-dc1-001",
  "power_state": "power on",
  "provisioning_state": "enroll",
  "maintenance": false

Step B: Move node to "Manageable" state (Ironic validates it can manage the server)

### Ironic State Machine (Node Lifecycle)

```
Enroll (raw info entered)
  ↓
Verifying (Ironic tests can reach BMC)
  ↓
Manageable (ready for provisioning)
  ├→ Cleaning (wipe disks, reset BIOS)
  │  ↓
  └→ Available (ready for users)
       ↓
     Deploy (Ironic provisioning OS)
       ↓
     Active (OS running, user has server)
       ↓
     Power off / Reboot as needed
       ↓
     Deleting (user releases, wipe & cleanup)
       ↓
     Available (back in pool)
```

#### Step 2: Create Provisioning Request

**Who:** Platform team or application owner  
**When:** When ready to deploy  
**Output:** Ironic begins provisioning all 20 nodes

```bash
# Method 1: Via Ironic API (programmatic)

for i in {1..20}; do
  NODE_UUID=$(ironic node-list | grep "bm-a-dc1-00$i" | awk '{print $2}')
  
  ironic node-set-provision-state $NODE_UUID provide
  # Moves node: manageable → available (ready for provisioning)
  
  # Then deploy
  nova boot \
    --flavor baremetal-kube \
    --image ubuntu-22.04-k8s-node \
    --nic net-id=provisioning-net \
    kube-node-$i
  # Ironic intercepts, starts provisioning
done

# Method 2: Ansible (infra-as-code)

---
- name: Provision 20 servers for Kubernetes
  hosts: localhost
  tasks:
    - name: Get all available nodes
      shell: |
        ironic node-list --fields uuid name provisioning_state \
          -f csv | grep available
      register: available_nodes
    
    - name: Deploy OS to each node
      shell: |
        nova boot \
          --flavor baremetal-kube \
          --image ubuntu-22.04-k8s-node \
          --nic net-id=provisioning-net \
          --hint reservation={{ item.uuid }} \
          kube-node-{{ index }}
      loop: "{{ available_nodes.stdout_lines }}"
```

#### Step 3: Ironic Provisioning Workflow (Internal)

**Who:** Ironic conductor (automatic)  
**When:** When deploy is triggered  
**Duration:** ~10-15 minutes per server  
**Output:** OS installed, server boots into production

```
For each of 20 servers:

PHASE 1: Power Down & Reset
  └─ Ironic calls BMC: "Set boot device to PXE"
     Command (IPMI): ipmitool -H 10.0.0.45 chassis bootdev pxe options=efiboot
     BMC does: Updates BIOS boot order (persists until changed)
  
  └─ Ironic calls BMC: "Power off"
     Command: ipmitool -H 10.0.0.45 power off
     Server: Graceful shutdown → off (30 sec)
  
  └─ Ironic calls BMC: "Power on"
     Command: ipmitool -H 10.0.0.45 power on
     Server: POST (Power-On Self-Test) → Firmware checks → looks for boot device

PHASE 2: PXE Boot into Provisioning
  └─ Server BIOS sees "boot device = PXE"
  
  └─ Server sends DHCP request on VLAN 200 (provisioning)
     DHCP server (run by neutron) responds:
     - IP: 10.100.0.50 (first in range)
     - Gateway: 10.100.0.1
     - Next server (TFTP): 10.100.0.1
     - Filename: pxelinux.0 (or grub2/grubx64.efi for UEFI)
  
  └─ Server fetches pxelinux.0 via TFTP
  
  └─ Server loads pxelinux.0, displays menu (or auto-boots)
     Menu shows:
       [ ] Boot from disk
       [X] Ironic Provisioning
       [ ] Rescue/Debug mode
  
  └─ Server boots into Linux kernel (3MB) + initramfs (50MB) from TFTP
     (This is downloaded in ~5 seconds over network)
  
  └─ Kernel loads, mounts initramfs as root, launches provisioning agent
     Agent is a small Python service that:
     - Mounts /dev/sda
     - Writes partition table
     - Formats partitions
     - Extracts OS image via HTTP from Glance
     - Runs disk I/O tests
     - Sets up bootloader (GRUB)
     - Reports progress to Ironic

PHASE 3: Download & Write OS Image
  └─ Ironic provides temporary download URL for ubuntu-22.04-k8s-node image
     URL: https://glance.dc1.internal/v2/images/f47ac10b.../data
     (URL signed with token, valid for 1 hour)
  
  └─ Provisioning agent (on server) downloads image:
     curl https://...image.../data | tar xz - > /dev/sda1
     
     Actually, more like:
     wget -O- https://...image.../data | dd of=/dev/sda1 bs=4M
     
     Speed: 1 TB image over 10 Gbps NIC = ~12 minutes
            (If disk is local NVME, write speed is bottleneck)

PHASE 4: Configure & Install Bootloader
  └─ Agent edits /etc/fstab (mount points)
     old: UUID=xxxxx / ext4 defaults 0 1
     new: UUID=<actual-uuid-on-this-server> / ext4 defaults 0 1
  
  └─ Agent installs GRUB bootloader:
     grub-install /dev/sda
     grub-mkconfig -o /boot/grub/grub.cfg
  
  └─ Agent does final verification:
     - Can read /boot? ✓
     - Can read /? ✓
     - Bootloader written? ✓
  
  └─ Agent reports to Ironic: "Provisioning successful, rebooting"

PHASE 5: Reboot into Production OS
  └─ Ironic calls BMC: "Reboot"
     Command: ipmitool -H 10.0.0.45 power off
             wait 5 sec
             ipmitool -H 10.0.0.45 power on
  
  └─ Server boots: BIOS → bootloader searches disk (no more PXE)
  
  └─ Bootloader finds GRUB on /dev/sda1
  
  └─ GRUB menu (30 sec timeout, auto-select if no input)
  
  └─ Kernel loads, init system starts (systemd)
  
  └─ Cloud-init runs (if enabled):
     - Sets hostname: kube-node-1
     - Configures NICs: eth0 gets 10.100.0.50, eth1 bonds
     - Runs user-data script (if provided)
  
  └─ SSH becomes available
  
  └─ Kubernetes Node Agent (kubelet) starts:
     - Registers with Kubernetes API server
     - Reports: "Node ready with 32 CPUs, 128 GB RAM, 1 TB disk"
     - Joins cluster

PHASE 6: Ironic Verification
  └─ Ironic polls node via SSH:
     Test SSH connection, verify /etc/os-release = Ubuntu 22.04 ✓
  
  └─ Ironic updates node state: "active"
  
  └─ Ironic stores in CMDB:
     {
       "node": "bm-a-dc1-001",
       "provisioning_state": "active",
       "power_state": "power on",
       "os": "Ubuntu 22.04 LTS",
       "kernel_version": "5.15.0-60-generic",
       "uptime": "2 min",
       "last_provision_timestamp": "2024-03-16T22:35:00Z"
     }

Timeline per server:
  [0:00] Ironic receives provision request
  [0:30] Server power cycles, PXE boots
  [1:00] Provisioning agent starts, contacts Ironic
  [1:30] OS image download begins
  [13:30] OS image downloaded, written to disk
  [14:00] Bootloader installed
  [14:30] Reboot into production OS
  [15:30] Cloud-init runs, kubelet starts
  [16:00] Kubernetes detects node ready
  [16:30] Ironic marks state "active"
  
Total: ~15-17 minutes per server
For 20 servers in parallel: ~17 minutes (not 20 × 17 = 340 min)
```

**Output:** 20 servers running Ubuntu 22.04, joined to Kubernetes cluster, ready for workloads.

### Day-2 Monitoring & Maintenance (Ongoing)

#### Scenario 1: Disk Failure on Server 3

```
Reality: Hard drive on bm-a-dc1-003 fails

Detection:
  1. Kernel logs disk I/O errors (SATA link down)
  2. Kubernetes detects node not responding (5 min threshold)
  3. Prometheus alerts: "Node bm-a-dc1-003 unreachable"
  4. On-call engineer receives PagerDuty alert

Investigation (via Ironic):
  ironic node-show bm-a-dc1-003 --fields power_state maintenance
  
  Output:
  power_state: power on

  # But Kubernetes says it's dead. Let's check console output.

    5. Tech powers on (or Ironic does via BMC)

    7. Kubernetes detects node, reschedules pods

### Step 2: Secure Data Wipe

**Who:** Platform team (automated via Ironic)  
**Duration:** 1-2 hours (depends on disk size)  
**Output:** Disk completely wiped, all data unrecoverable

```bash
# Ironic cleaning process (built into node state machine)

# Transition node: manageable → cleaning

ironic node-set-provision-state bm-a-dc1-001 deleted
(Triggers automatic cleanup on delete)

# Behind the scenes, Ironic:

1. Power off server (via BMC)
   ipmitool -H 10.0.0.45 power off

2. Set boot to PXE (via BMC)
   ipmitool -H 10.0.0.45 chassis bootdev pxe

3. Power on (via BMC)
   ipmitool -H 10.0.0.45 power on

4. Server boots into cleaning ramdisk (special Linux image, ~50MB, from TFTP)

5. Cleaning agent runs cleaning steps:
   
   Step A: Wipe all disks
     # For each disk (/dev/sda, /dev/sdb, etc.)
     shred -n 3 -z -f /dev/sda  # 3 passes: random data, random data, zeros
     # (NIST standard for data destruction)
     # Speed: ~100-200 MB/s depending on disk, so:
     # 1 TB disk = 5-10 hours at bare minimum
     
     # OR (faster for SSD):
     hdparm --security-erase-unit /dev/sda
     # Uses ATA secure erase command, nukes entire SSD in ~1 min
     
     # Verification:
     # Read from disk: only zeros/random data, no previous data recoverable
   
   Step B: Clear BIOS/UEFI settings
     echo "" | dmidecode --no-sysfs
     (Reset to defaults)
   
   Step C: Generate cleaning report
     report = {
       node: bm-a-dc1-001,
       cleaning_steps_completed: [
         "wipe_disk_sda",
         "wipe_disk_sdb",
         "clear_bios"
       ],
       timestamp: 2024-03-17T14:00:00Z,
       status: "success"
     }
   
   Step D: Power off (cleaning complete)
     ipmitool -H 10.0.0.45 power off

6. Ironic verifies:
   ironic node-show bm-a-dc1-001 --fields provision_state
   Output:
   provision_state: cleaned

# Alternative: Manual wipe (if automated fails)

# Tech connects to server console via BMC:
ipmitool -H 10.0.0.45 -I lanplus sol activate

# Boot into live USB (Secure Boot disabled via BMC)
# Run: dd if=/dev/zero of=/dev/sda bs=4M  (full disk zero)
# Time: 1-10 hours depending on disk type

# Update CMDB
ironic_cleanup_record = {
  node: bm-a-dc1-001,
  wipe_method: "NIST_3_pass",
  wipe_duration_min: 180,
  wipe_completion: 2024-03-17T14:00:00Z,
  disk_status: "securely_erased",
  ready_for_disposal: true
}
```

**Duration:** 30 min  
**Output:** Server removed from rack, disconnected from power/network

## Conclusion

**The complete flow is:**

1. **Day-0**: Hardware → Ironic-managed infrastructure
   - Your truck unloads servers → techs physically mount them → network team cables them → platform team sets up BMC + Ironic
   - Result: Ironic can talk to all servers

2. **Day-2**: Ironic orchestrates entire server lifecycle
   - Provision (PXE boot → OS install) in parallel across fleet
   - Monitor (BMC telemetry + Kubernetes integration)
   - Update (re-provision with new image during rolling updates)
   - Repair (power cycle, reboot, health checks via BMC)

3. **Cleanup**: Secure removal from service
   - Migrate workloads → wipe disks (NIST-compliant) → physically remove → RMA/recycle

**BMC is the enabler:** Out-of-band management allows Ironic to control servers without OS access.  
**Ironic is the orchestrator:** Automation layer that talks to BMCs and manages server state.  
**Kubernetes is the consumer:** Treats servers as cattle, requests workload placement.

All three layers must work together seamlessly for a modern cloud-scale datacenter.
